# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Gestik ("Kainos Suite") — an internal CRM for a freelance/agency business to manage clients, recurring services, payments, and fixed/one-off expenses. Next.js 16 (App Router) + React 19 + TypeScript, backed directly by Postgres (no ORM). All UI text, identifiers, and comments are in Spanish — follow that convention in new code.

## Commands

```bash
npm run dev             # start dev server (Next.js, Turbopack)
npm run build            # production build
npm run start             # run production build
npm run lint               # eslint (flat config: eslint-config-next core-web-vitals + typescript)

npm run migrate:up         # apply pending Postgres migrations (node-pg-migrate)
npm run migrate:down        # roll back the last migration
npm run migrate:create <name> # scaffold a new migration file in migrations/
```

There is no test runner configured in this repo (no test script, no Jest/Vitest dependency).

Migrations need `DATABASE_URL` set (see `.env`, gitignored). node-pg-migrate reads it via the `DATABASE_URL` env var by default. The app also requires `SESSION_SECRET` and `SITE_PIN` (see Auth below), plus `CRON_SECRET` (see cron job below).

## Architecture

**No ORM.** Prisma was removed (see git history, "goodbye Prisma"). Database access is raw SQL through a single shared `pg.Pool` in `src/lib/db.ts`, cached on `globalThis` so hot-reload in dev doesn't exhaust connections. Schema changes go through `node-pg-migrate` migration files in `migrations/` — there is no `schema.prisma` or generated client to keep in sync.

Postgres enums back the domain's state machines (`estado_cliente`, `tipo_servicio`, `frecuencia_servicio`, `estado_servicio`, `metodo_pago`, `categoria_gasto`, `frecuencia_gasto`, `estado_gasto_fijo`, `modalidad_pago_cliente`, `origen_fondos` — defined across `migrations/…create-tablas-iniciales.js`, `migrations/…crear-tablas-gastos.js` and `migrations/…agregar-modalidad-pago-a-clientes.js`; `estado_cargo`, `estado_pago_gasto_fijo` and `estado_deuda` don't exist as DB enums, they're computed — see below). Zod schemas re-declare the same value sets as the single source of truth on the app side (e.g. `ESTADOS_CLIENTE` in `src/features/clients/schema.ts`) — when adding a new enum value, update both the migration and the corresponding Zod schema. One exception: the `moneda` enum (`ARS`/`USD`, migration `…agregar-moneda.js`) is cross-cutting — `servicios`, `cargos`, `pagos`, `gastos_fijos` and `gastos` all carry it, so its single source of truth lives in `src/lib/moneda.ts` (`MONEDAS`, `Moneda`, `formatCurrency`) instead of being re-declared per feature.

**Feature-based structure** under `src/features/<feature>/`, one directory per domain area (`clients`, `services`, `cargos`, `pagos`, `gastos`, `deudas`, `finanzas`, `dashboard`, `balance-mensual`). Each feature is organized by responsibility rather than by component:
- `queries.ts` — read functions, `pool.query(...)` → mapped rows. Called from Server Components.
- `actions.ts` — `'use server'` mutations, called from client components/forms. Validate input with the feature's Zod schema, then write via `pool.query`, then `revalidatePath(...)`. `finanzas` and `dashboard` have no `actions.ts` — they're pure read/aggregate features (queries + components only). `cargos` has no `actions.ts` or `schema.ts` either: cargos are only ever written by `services/actions.ts` (create/renew/edit of a servicio), so that feature is queries/types/services/components.
- `schema.ts` — Zod schemas (validation + inferred `*Input` types). Enum arrays here must mirror the Postgres enum definitions.
- `types.ts` — hand-written domain types plus a `mapX(row): X` function that converts a raw Postgres row (snake_case columns) into the camelCase shape the app uses. Any new query result must go through one of these mappers, not be used raw.
- `services.ts` (where present) — pure business-logic helpers with no I/O, e.g. `calcularEstadoCargo` in `cargos/services.ts` (derives PENDIENTE/PARCIAL/PAGADO/VENCIDO from how much of a cargo is covered), `calcularProximoVencimiento` in `services/services.ts` (computes next due date from frequency), and the equivalent pair in `gastos/services.ts` — `calcularProximoVencimiento` (MENSUAL/MENSUAL_30_DIAS/ANUAL) and `calcularEstadoPagoGastoFijo` (AL_DIA/VENCIDO, UTC-based date comparison to avoid timezone off-by-one). `deudas/services.ts` has `calcularEstadoDeuda` (same ACTIVA/SALDADA-from-coverage pattern) and `calcularMontoReposicion` (cross-currency conversion, see domain model below). `pagos/services.ts` has the analogous `calcularMontoAcreditado` (a client paying a USD-priced service in ARS, or vice versa — see domain model); payment-*status* logic (PENDIENTE/PARCIAL/PAGADO/VENCIDO) still lives in `cargos`, not here. `balance-mensual/services.ts` has `calcularReparto`, the pure 30/30/40 split (see domain model).
- `components/` — feature-scoped React components (dialogs, forms, tables).

Some files carry stale header comments referencing older folder names (e.g. `clients/actions.ts` still says `// src/features/clientes/actions.ts`, `services/services.ts` says `servicios`) from a since-renamed directory. These are cosmetic leftovers, not a sign the file is in the wrong place — trust the actual file path over the comment.

**Routing**: pages live under the `(dashboard)` route group (`src/app/(dashboard)/`: `dashboard`, `clients`, `services`, `pagos`, `gastos`, `gestion` — note `deudas` has no route of its own, it's a tab inside `gastos`, see domain model below), sharing a layout (`src/app/(dashboard)/layout.tsx`) that renders `Sidebar` + `Topbar` around the page content and forces `dynamic = 'force-dynamic'`. Nav entries are hardcoded in `src/components/layout/sidebar.tsx` (`NAV_ITEMS`) — add a link there when adding a new top-level page. **The folder names and the nav labels no longer match**: `/dashboard` is labeled "Balance Mensual" in the sidebar (monthly money in/out — this, last and next month — plus the sueldo/gastos/ahorro reparto), while `/gestion` is labeled "Gestión General" (the original finanzas-style balance/ingresos/gastos content). This was a deliberate rename-in-place to avoid a bigger route migration — trust the nav label the user sees over the folder/route name when reasoning about "which page is this." The layout also wraps everything in `MobileNavProvider` (`src/components/layout/mobile-nav-context.tsx`): `Sidebar` is a fixed-position drawer below the `md` breakpoint (hidden by default, toggled by a hamburger button in `Topbar`, closes on backdrop click or nav), and reverts to the always-visible static sidebar at `md` and up. API routes: `src/app/api/servicios/por-cliente/route.ts` for a client-side selector fetch, and three daily cron routes under `src/app/api/cron/` (see below); everything else goes through Server Components (queries) or Server Actions (mutations), not API routes. `/login` is the one route outside the dashboard group/layout.

**Auth**: minimal shared-PIN gate, no per-user accounts (`src/lib/session.ts`). `src/proxy.ts` is this app's `middleware.ts` equivalent — Next.js 16 renamed the convention from `middleware` to `proxy`, but it's the same mechanism (matcher-scoped request interception before rendering). It runs on every route except `/login`, `/api/cron/*`, static assets, and the favicon, checks the `gestik_session` cookie via `isValidSessionToken`, and redirects to `/login` if missing/invalid. `src/app/login/actions.ts` (`iniciarSesion`/`cerrarSesion`) verifies the submitted PIN against `SITE_PIN` with a constant-time HMAC comparison (`verifyPin`) plus an artificial 500ms delay on failure, then sets an HMAC-signed cookie (`SESSION_SECRET`) valid 30 days. Session logic uses Web Crypto (`crypto.subtle`) rather than `node:crypto` specifically because it must run in both the Node server-action runtime and the Edge runtime of `proxy.ts`. `/api/cron/*` is excluded from the PIN gate on purpose — Vercel Cron calls it server-to-server with no session cookie, authenticated instead via `CRON_SECRET` (see below).

**Renovación automática de servicios, gastos fijos y repartos mensuales (crons)**: `vercel.json` schedules three daily hits (`0 9 * * *` UTC), one per route, all under `src/app/api/cron/`. All three check `Authorization: Bearer $CRON_SECRET` (Vercel auto-injects this header when the env var is named exactly `CRON_SECRET`). `renovar-servicios` calls `renovarServiciosVencidos()` in `services/actions.ts`: finds every `ACTIVO`, non-`UNICO` servicio whose `proximo_vencimiento` has passed and renews it — sharing the same per-cycle logic (`renovarUnCiclo`) as the manual "Renovar" button (`renovarServicio`), which still exists for early renewals or price changes (`nuevoPrecio`). If a servicio missed more than one cycle (e.g. the cron was down), it "catches up" by generating one cargo per missed period in a loop (capped at `MAX_CICLOS_CATCH_UP`), rather than collapsing to a single cargo. `estado` (`PAUSADO`/`FINALIZADO`) is what stops a servicio from auto-renewing — it isn't replaced or made redundant by this automation. `renovar-gastos-fijos` uses the same auth and calls `renovarGastosFijosVencidos()` in `gastos/actions.ts`: every `ACTIVO` gasto fijo whose `proximo_vencimiento` has passed gets a `gasto` generated (same catch-up loop, with its own `MAX_CICLOS_CATCH_UP`), sharing `renovarUnCicloGasto` with the manual `registrarGastoDelMes`. `renovar-repartos-mensuales` calls `renovarRepartosMensuales()` in `balance-mensual/actions.ts` — see that feature in the domain model below for what it does and why it can stop short of catching up every pending month.

**Data flow for client-driven mutations**: forms use `react-hook-form` + `@hookform/resolvers` bound to the feature's Zod schema, submit through a `useMutation` hook in `src/hooks/` that calls the server action, invalidates the relevant TanStack Query key, and shows a `sonner` toast on success/error (see `src/hooks/use-crear-cliente.ts` as the pattern to follow). `QueryClient` is set up once in `src/app/providers.tsx` (1 min `staleTime`, no refetch-on-focus — deliberate for an internal CRM's low write-contention usage).

**UI kit**: shadcn/ui components in `src/components/ui/` (style `base-vega`, Tailwind base color `neutral`, no `tailwind.config` — Tailwind v4 config lives in `src/app/globals.css`). Icons from `lucide-react`. Shared non-primitive components (data table, status badge, `chart-detalle-card`, `meses-detalle-tabla`) live in `src/components/shared/`. `src/lib/constants.ts` centralizes label/style maps for enum values (`ESTADO_STYLES`, `TIPO_SERVICIO_LABELS`, etc.) — extend these when adding a new enum value instead of inlining labels in components. **Whenever a `<Select>` is used, give `SelectValue` a children render-function** (`{(value) => LABELS[value] ?? value}`) that looks up the label — without it, the closed trigger shows the raw enum value (e.g. `DESARROLLO_WEB`) instead of the label until the dropdown has been opened once; this bit several forms before being standardized. `src/lib/client-colors.ts` defines the curated 16-color palette used to visually tag clients across tables (assigned rotationally by signup order via `pickClientColor`, persisted as `clientes.color`) — kept visually distinct from the green/yellow/red `ESTADO_STYLES` badge colors.

**Theme**: `src/app/globals.css` defines a single dark theme (brand black/orange/gray) in `:root` *and* `.dark` identically — `next-themes` is a dependency but was never wired up (no `ThemeProvider`, no toggle), so there's deliberately no light mode to fall back to. `src/components/ui/tooltip.tsx` wraps `@base-ui/react/tooltip` the same way `popover.tsx` wraps its popover primitive.

**Mobile nav**: `src/components/layout/mobile-nav-context.tsx` (`MobileNavProvider`/`useMobileNav`) holds the open/closed state that `Sidebar` and `Topbar` both need (they're siblings, not parent/child) — below the `md` breakpoint `Sidebar` renders as a fixed-position drawer with a backdrop, opened by a hamburger button in `Topbar`.

**Responsive forms**: any two-column `grid grid-cols-2` pairing a plain field with a composite "monto + moneda `<Select>`" field (see `services/schema.ts`-style forms) needs `grid-cols-1 sm:grid-cols-2`, not bare `grid-cols-2` — on a phone-width viewport the composite field's inner `flex` row has no room and the amount input gets crushed to a sliver. Check for this pattern whenever adding a new form with a currency-paired field.

**React Compiler** is enabled (`next.config.ts` → `reactCompiler: true`, via `babel-plugin-react-compiler`) — avoid manual `useMemo`/`useCallback` micro-optimizations that fight the compiler; write plain component code.

## Domain model

- **clientes** (`clients` feature) — customers, `estado` ACTIVO/PAUSADO/FINALIZADO, each with a rotationally-assigned `color` (see UI kit above) for at-a-glance identification, and a `modalidad_pago` (`ANTICIPADO`/`POSPAGO`, default POSPAGO for pre-existing clients) that decides when their cargos fall due (see cargos).
- **servicios** (`services` feature) — recurring or one-off services sold to a client, `frecuencia` UNICO/MENSUAL/ANUAL drives `proximo_vencimiento` calculation.
- **cargos** (`cargos` feature) — "lo que se debe cobrar" for a given period; generated automatically when a service is created or renewed (`crearServicio`/`renovarServicio` in `services/actions.ts`), copying the service's `precio` and `moneda` at that moment. A later price/currency change via `editarServicio` syncs any cargo for that service that isn't fully covered yet (PENDIENTE or PARCIAL — including one with some payment already applied) to the new `precio`/`moneda`, so "Cobros" doesn't keep showing a stale amount the service already moved on from. Only a cargo that's already covered 100% (PAGADO) is left untouched on purpose, so a price edit never rewrites under what amount a closed payment was made. `periodo` (cycle start) and `vencimiento` (payment due date) are tracked separately: `vencimiento` is the start of the *next* period (a MENSUAL/ANUAL cargo isn't overdue the instant it's created), while a UNICO service has no next period so it's due in its own `periodo`. The client's `modalidad_pago` changes this: `calcularVencimientoCargo` (`services/services.ts`) makes an ANTICIPADO client's cargo due at the start of its own `periodo` (pay before the work month), while POSPAGO keeps the next-period rule above. `calcularEstadoCargo` (`cargos/services.ts`) derives PENDIENTE/PARCIAL/PAGADO/VENCIDO from how much of the cargo has been covered and whether its `vencimiento` has passed.
- **pagos** (`pagos` feature) — a pure receipt of money received; has no `estado` of its own (dropped in migration `quitar-estado-de-pagos` — "ahora es un recibo puro"). Payments are matched against cargos with a waterfall: `getCargos()` (`cargos/queries.ts`) applies each service's payments against that service's cargos oldest-period-first, so a payment isn't tied to one specific cargo — two payments can fully cover one month and partially cover the next even if that's not how the user mentally split them. `pagos.monto`/`moneda` is what gets credited to the cargo, and it always mirrors the `moneda` of the service it's associated with (enforced server-side via `resolverConversion` in `pagos/actions.ts`, ignoring whatever currency the client submitted) — you cannot credit a service in a different currency than it's priced in. But the client can still *pay* in a different currency: `monedaPago`/`montoPagado` record what actually came in, and when it differs from the service's currency, `tipoCambio` (same "ARS per USD" convention as `deudas`) converts it via `calcularMontoAcreditado` (`pagos/services.ts`) — the same credited-amount-vs-what-actually-left-pocket shape as a `reposicion_deuda`'s `monto` vs `montoPagado`/`monedaPago`. If there's no servicio associated (a standalone pago), there's no currency to convert *to*, so `monto`/`moneda` are just set equal to `montoPagado`/`monedaPago`.
- **gastos_fijos / gastos** (`gastos` feature) — the expense-side mirror of servicios/pagos: `gastos_fijos` is a recurring expense definition (`categoria`, `frecuencia` MENSUAL/MENSUAL_30_DIAS/ANUAL, `estado` ACTIVO/PAUSADO/FINALIZADO), `gastos` is each actual outflow (optionally linked back via `gasto_fijo_id`, nullable for one-off expenses). Unlike cargos/servicios, payment status here isn't persisted at all — `calcularEstadoPagoGastoFijo` computes AL_DIA/VENCIDO on the fly from `proximo_vencimiento` vs. today (UTC-normalized to avoid timezone drift), and only for ACTIVO gastos fijos. MENSUAL_30_DIAS (added in a later migration, `after: 'MENSUAL'` in the enum) is for subscriptions that bill every 30 days from the last charge rather than the same calendar day each month (e.g. Adobe), which calendar-based MENSUAL can drift against.
- **integrantes / deudas / reposiciones_deuda** (`deudas` feature) — tracks money a team member (`integrante`) fronted out of pocket for the business (`deuda`) that the company owes back, repaid incrementally (`reposicion_deuda`). `integrantes` exists solely to answer "who fronted this money" — there's no concept of app users otherwise (PIN-only auth, see Auth). Like `cargos`/`gastos_fijos`, a deuda's status isn't persisted: `calcularEstadoDeuda` (`deudas/services.ts`) derives ACTIVA/SALDADA from `montoTotal` vs. the summed `monto` of its reposiciones (computed in `getDeudas()`/`getDeudaById()`, not stored). A reposición carries two amounts that can diverge: `monto` (credited to the deuda, in the deuda's own `moneda`) vs. `montoPagado`/`monedaPago` (what actually left pocket) — when the two currencies differ, `tipoCambio` (always "how many ARS per 1 USD") converts between them via `calcularMontoReposicion`, and the server action re-validates that a cross-currency reposición carries a `tipoCambio` even though the Zod schema can't (it doesn't know the deuda's currency). No dedicated route/nav entry — it's rendered as a "Deudas" tab inside `/gastos` (`src/app/(dashboard)/gastos/page.tsx`), and its monthly totals (`getTotalReposicionesDeudaMes`, grouped by `monedaPago` since that's what actually hits the wallet) are pulled into `/gestion`'s balance calculation, subtracted alongside `gastos`. Don't confuse this with `clientesConDeuda` in `finanzas` — that's the unrelated, pre-existing concept of clients owing the business money via unpaid `cargos`.
- **finanzas / gestion** — aggregate reporting (income by month/client, outstanding debt via `cargos`, payment history) over `pagos` and `cargos`. The page lives at the `/gestion` route (renamed from `/finanzas`) but is labeled **"Gestión General"** in the nav — see Routing above for why the route and the nav label stopped matching. It still reads from `src/features/finanzas/`, which is query-only (no mutations of its own).
- **repartos_mensuales** (`balance-mensual` feature, no route of its own — rendered inside `/dashboard`, the page labeled "Balance Mensual") — once a month is over, its Facturado (see `getCargosFacturadoMes` in `dashboard/queries.ts`, parameterized by month) gets split 30% sueldos / 30% gastos-fijos-y-deudas / 40% ahorro (`calcularReparto`; was 30/50/20 until migration `…recalcular-repartos-30-30-40`, which rewrote the already-frozen rows too) and frozen into one row, generated on the 1st of the *following* month by the `renovar-repartos-mensuales` cron (see Crons above). Sueldos and gastos-fijos-y-deudas stay split by moneda (ARS/USD, unconverted); ahorro is the one deliberate exception — it's always folded into a single ARS figure (`ahorro_mes_ars`), because it physically sits in Mercado Pago reserves, so a USD month's ahorro portion needs `tipoCambio` to convert. That's also why a month with `facturado_usd > 0` can't auto-generate: `getMesesPendientesDeReparto` (`balance-mensual/queries.ts`) surfaces it, the dashboard shows a gate (`TipoCambioMensualGate`) asking someone to enter that month's rate, and `registrarTipoCambioMensual` generates it (then keeps going through any later zero-USD months in the same catch-up pass). "Plata disponible en cuenta" is *not* stored — `getDisponibleEnCuenta()` derives it each time, per moneda (ARS/USD, unconverted), as (everything ever apportioned to gastos-fijos-y-deudas) minus (gastos with `origen_fondos = 'CUENTA'` plus reposiciones-de-deuda by `moneda_pago`, paid since the first reparto's month); "Caja de ahorro" (`getCajaDeAhorro()`) is the sum of `ahorro_mes_ars` minus gastos with `origen_fondos = 'CAJA_AHORRO'` (ARS only — `validarOrigenFondos` in `gastos/actions.ts` rejects a USD gasto paid from the caja). `gastos.origen_fondos` (enum `origen_fondos`, migration `…agregar-origen-fondos-a-gastos`) is required in the "Registrar gasto" form with no default; gastos generated from a gasto fijo are always `CUENTA`; pre-existing one-off gastos stay NULL and count against neither balance. Clicking either card opens its last 10 movements with a running balance (`getMovimientosCuenta`/`getMovimientosAhorro`, same inclusion rules as the totals, each reparto dated the 1st of the following month) — keep those queries and `getDisponibleEnCuenta` in sync, or the newest row stops matching the card — it's explicitly an approximation, and can start out negative for a business that already had expenses before this feature existed (no reparto ever apportioned money for those). **Gotcha**: any `Date` representing a bare calendar month that round-trips through a `pool.query` parameter must go through `dateToSqlDateString` (`src/lib/utils.ts`) first — `pg` serializes a raw JS `Date` using its *local*-timezone getters, so a UTC month-start like `2026-09-01T00:00:00Z` silently becomes August in a negative-UTC-offset environment (e.g. Argentina) once it's cast `::date` server-side. This bit `getCargosFacturadoMes`'s month parameter and `generarReparto`'s insert before being fixed.
- **moneda** (ARS/USD, `src/lib/moneda.ts`) — every money-bearing table (`servicios`, `cargos`, `pagos`, `gastos_fijos`, `gastos`, `deudas`, `reposiciones_deuda`) carries a `moneda` (or `moneda_pago`) column; `repartos_mensuales` instead splits ARS/USD into separate columns per metric (`sueldos_ars`/`sueldos_usd`, etc. — see domain model above), since it has no single natural "the moneda of this row". Amounts are never converted or summed across currencies — every aggregate query (`getSaldoPorCliente`, `getKpis`, `getIngresosPorMes`, etc.) groups by `moneda` and returns one row/series per currency instead of a single blended total. `gastos`/`gastos_fijos` follow the same inherit-don't-choose pattern as pagos: a `gasto` tied to a `gastoFijoId` takes that fijo's `moneda` server-side. The deliberate exceptions to "never converted" are `reposiciones_deuda.tipo_cambio`, `pagos.tipo_cambio` (both ARS-per-USD, per-row, see their domain model entries above) and `repartos_mensuales.tipo_cambio` (same convention, applied once per month to fold that month's USD ahorro into `ahorro_mes_ars`).
